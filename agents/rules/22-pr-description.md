## PR descriptions
Write the description for a human reviewer who did not watch the work: plain language, short, and skimmable, with no internal jargon or names you made up. It never contains a test plan: the tests run in CI, and code that cannot be tested is not submitted, so a promise to test by hand is not a substitute. It holds four things. First, why the change exists: the problem or need, in a sentence or two, before anything about how. Second, what the increment does, in a few lines. Third, a manual QA plan: what to open, run or click to see the increment working, as exact commands or steps. Fourth, a link to the live environment it deployed to, if any. When the change needs anything beyond merging to take effect or to be checked (a migration, a config or env change, a `tars pull`, a restart, a seed, a manual step on another system), list those as explicit extra steps with the exact commands, so nobody discovers them after the merge.
