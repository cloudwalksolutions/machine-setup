## Comments
Comments are for users, not maintainers; tests are for maintainers. A comment explaining how or why code works is documentation nothing checks: it has to be maintained by hand, goes stale the moment the code moves, and then misleads. A test is executable and documents the key behavior for the use case, and it fails when it stops being true. So put intent in names and tests, and the why in the commit or PR, never in a comment that will rot. An ugly comment is one that compensates for a missing test or unreadable code: a header block saying what a file does, a line restating the name under it, a note in a test or config file. The urge to write one is a signal to stop and ask why the code needed explaining. Often it does not: the spec already states the behavior and the comment is noise. When it does, the code is unclear, and the fix is to its structure: split the function, extract the step, reorder the flow, move the logic to where its context already lives, then name the parts. Clean code reads without a comment.
