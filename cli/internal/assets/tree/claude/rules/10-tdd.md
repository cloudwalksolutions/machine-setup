## TDD, strictly
Write ONE failing test, run it and see it red, then write the minimal code to make it green, then refactor. Never write source ahead of a failing test and never batch several tests. Tests are the oracle: run the affected suites after every change and the full suite before saying anything is done. Let a failing test localize a bug instead of guessing at fixes. Tests are the source of truth for behaviour, so docs never restate what a test, check or alert proves, and never point at tests; they hold only what tests cannot, such as hardware, hand-configured external state, operator procedures and look-alike failure modes. A requirement nothing proves gets a test, not a paragraph.
