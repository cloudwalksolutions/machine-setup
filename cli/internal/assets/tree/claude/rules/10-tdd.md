## TDD, strictly
Write ONE failing test, run it and see it red, then write the minimal code to make it green, then refactor. Never write source ahead of a failing test and never batch several tests. Tests are the oracle: run the affected suites after every change and the full suite before saying anything is done. Let a failing test localize a bug instead of guessing at fixes. A red must fail because the behavior is missing, not from a typo, import, selector or setup error. Work outside-in, error and edge cases before the happy path. Fix a bug the moment you find it, starting with a failing test that reproduces it and stays as its regression test. Tests are the source of truth for behaviour, so docs never restate what a test, check or alert proves, and never point at tests; they hold only what tests cannot, such as hardware, hand-configured external state, operator procedures and look-alike failure modes. A requirement nothing proves gets a test, not a paragraph.
