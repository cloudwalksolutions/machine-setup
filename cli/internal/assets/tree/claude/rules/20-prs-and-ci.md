## Pull requests and CI
Land work as small, focused pull requests, one increment each, and prefer many small changes to main; use a release branch (dev, stage…) only when the repo already has one or releases genuinely need batching. Never push to a protected branch, never `git stash`, never rewrite pushed history. Prove validity with tests that run in CI; a green local run is not proof, and nothing is done while CI is red or unverified. A PR description is concise: the increment the code adds (not the testing plan), QA steps, and a link to the live environment it deployed to, if any. Send the PR link as soon as it is ready, and delete the local branch once it merges.
